# Security Model

## Authentication & sessions

- Admin passwords are hashed with `bcryptjs` (cost factor 12, salted per-password) — `src/lib/password.ts`.
- Sessions are stateless JWTs (`jose`, HS256) signed with `SESSION_SECRET`, stored in an `httpOnly`, `SameSite=Lax` cookie, `secure` in production, 8-hour expiry — `src/lib/sessionToken.ts`, `src/lib/session.ts`.
- `src/middleware.ts` verifies the session on every `/admin/*` page and `/api/*` route (except `/api/auth/login` and `/api/public/*`), and stamps the verified `adminId`/`role` onto trusted `x-admin-id`/`x-admin-role` request headers for route handlers to read — **any client-supplied values for those exact header names are stripped first**, so a request cannot spoof its own identity.
- Login responses are identical (`"Invalid email or password"`, same status) whether the email doesn't exist or the password is wrong, and a fixed dummy bcrypt hash is compared on unknown-email attempts, to resist user enumeration by content or gross timing.
- Login attempts are rate-limited per IP (`src/lib/rateLimit.ts`).

## CSRF

Since admin auth is cookie-based, state-changing requests (`POST`/`PUT`/`PATCH`/`DELETE`) to any non-public API route are rejected in middleware unless their `Origin` header matches the app's own origin. Verified live: a cross-origin `POST` with a cookie returns `403`.

## Certificate integrity (the core trust guarantee)

- Every certificate stores a `verificationHash` = `SHA-256(canonicalized certificate data + CERT_HASH_SECRET)` (`src/lib/crypto.ts`). The secret never leaves the server, so a certificate row cannot be fabricated or edited to pass verification without it.
- The public verify endpoint (`/api/public/verify/:uid`, and the `/verify/[uid]` page that shares the same code path) recomputes and compares the hash on every lookup and reports `status: "invalid"` on mismatch, using a timing-safe comparison (`timingSafeEqual`).
- Certificates are **never deleted**: `revoke` and `reissue` only change `status` (`active` → `revoked`/`superseded`), so a QR code keeps resolving forever, per the spec's permanence requirement.
- Certificate ids are validated against a strict format allowlist (`isValidCertificateUidFormat`) *before* any database or filesystem lookup, closing off path-traversal-shaped input (e.g. `../../etc/passwd`) at the door.
- **Found and fixed during review**: `POST /api/templates` accepted an arbitrary string for `backgroundUrl`, which was later joined onto a filesystem path and read to embed as the certificate background (`src/lib/certificateService.ts`). A `backgroundUrl` like `../../../../etc/some-file` would have been read from disk and embedded into a certificate PDF — one served *without authentication* via `/api/public/verify/:uid/pdf` to anyone holding the certificate UID (which isn't secret; it's printed on the certificate). Fixed by restricting `backgroundUrl` in `templateInputSchema` to exactly what an upload endpoint returns — a local `/uploads/<category>/<filename>.<ext>` path or an `https://` URL on the trusted Vercel Blob host (`isTrustedImageReference` in `src/lib/imageUrl.ts`) — checked again at read time before any local read or remote fetch, as defense-in-depth. See "File uploads" below for the follow-on SSRF consideration this raised once image storage became a fetchable remote URL. Covered by `tests/unit/imageUrl.test.ts`, `tests/unit/storage.test.ts`, and `tests/unit/validation.test.ts`.
- Sequence numbers for certificate ids are scoped to the full `prefix-year-programCode` combination (not the internal program row id) — an earlier version of this scoped sequences per-program instead, which a test caught: two programs that happen to produce the same human-readable code would have collided on the same certificate id. Fixed and covered by `tests/unit/certificateId.test.ts` and `tests/integration/certificates-api.test.ts`.
- **Displayed certificate content is frozen at issuance** (`renderedSnapshotJson`), not re-derived from live `Participant`/`TrainingProgram` rows on every render — see README.md's "How a certificate stays permanent" section. This matters more now that PDFs render on demand (below) rather than once at generation time: without a frozen snapshot, editing a program's title after certificates were issued would silently change what an already-issued "permanent" certificate displays on every future view.

## File uploads

- Signature/logo uploads (`src/lib/storage.ts`) are restricted to `image/png`, `image/jpeg`, `image/webp`, capped at 2MB, and stored under a **server-generated random filename** (never the client-supplied name) — the client-provided name is never used to construct a path or storage key, so it cannot escape the upload directory or overwrite another file.
- In production, uploads go to Vercel Blob (public access, since these are non-sensitive branding images referenced from public certificates anyway); locally, they fall back to `public/uploads/<category>/`.
- **SSRF consideration**: once an image reference can be an arbitrary-looking `https://` URL (Blob storage) rather than only a local path, the certificate-rendering code path that fetches it (`loadImageBytes` in `src/lib/storage.ts`) becomes a place a lower-privileged Admin/Program Coordinator (not just Super Admin — template creation isn't Super-Admin-gated) could point at an internal or attacker-controlled host if left unchecked. `isTrustedImageReference` allowlists only our own Blob host (`*.public.blob.vercel-storage.com`) over HTTPS, or a local `/uploads/...` path — nothing else is ever fetched or read, regardless of what's stored in `backgroundUrl`/`signatureUrl`. Covered by `tests/unit/imageUrl.test.ts` (including an explicit "rejects... 169.254.169.254" cloud-metadata case) and `tests/unit/storage.test.ts`.
- Bulk participant import files are capped at 5MB and parsed as CSV/XLSX only; every row is validated with `zod` before any database write.

## Security headers

Set on every request in `src/middleware.ts`: `Content-Security-Policy`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, restrictive `Permissions-Policy`.

`script-src` uses a fresh per-request nonce + `'strict-dynamic'` in production (Next.js's documented App Router CSP pattern — it auto-applies the nonce to the script tags it renders), with `'unsafe-eval'`/`'unsafe-inline'` allowed only outside production, since Next's dev-mode Fast Refresh runtime uses `eval()`.

**Found and fixed during review — this one slipped past all 65 passing tests and was only caught by manually driving the app in a real browser**: the first version of this CSP shipped a static `script-src 'self'` with no nonce, no `'unsafe-eval'`, no `'strict-dynamic'`. That's stricter-looking but wrong for a Next.js app — Next's client runtime couldn't execute *at all* under it. Every test in the suite talks to route handlers directly, so nothing exercised the browser's actual CSP enforcement; the failure mode was also silent (no thrown error a test could catch) — the login form just fell back to a native HTML form GET submission with the credentials in the URL, and every other client-side interaction on the site would have been equally broken. Fixed by moving CSP generation into `src/middleware.ts` with the nonce/strict-dynamic pattern above, and covered going forward by `tests/unit/middleware.test.ts`, which asserts the production CSP has no `unsafe-eval`/`unsafe-inline` in `script-src` and the dev CSP does. Still worth a manual click-through after any further CSP change — this class of bug is specifically the kind unit/integration tests calling route handlers directly cannot see.

**Found again, in production this time, after real deployment**: fixing the CSP above wasn't actually sufficient. Setting the nonce on the CSP *header* in middleware only tells the browser what nonce to require — Next.js separately needs to be told, on the *rendering* side, to stamp that same nonce onto the `<script>` tags it emits (its own webpack runtime, page chunks, hydration data — not just app code). That requires reading the nonce via `headers()` inside a Server Component in the render tree; without it, Next has no signal that nonce mode is active, so none of its own scripts carry one. Combined with `'strict-dynamic'` (which disables the normal host-based fallback), the result was that *every* script on *every* page was blocked outright — confirmed via a live user's browser console showing CSP violations on `webpack-*.js`, `main-app-*.js`, and Next's inline hydration scripts. This is strictly worse than the first CSP bug: that one broke interactivity silently; this one is a routine, easy-to-miss step in Next's own documented nonce pattern, and it reproduced in production despite `next build` succeeding, `npm test` passing, and an earlier local dev-mode click-through looking fine (dev mode's relaxed `'unsafe-eval'`/`'unsafe-inline'` script-src masked it entirely — the missing-nonce problem only bites under the strict production CSP branch). Fixed with one line in `src/app/layout.tsx` — `headers()` called in the root layout, unused otherwise — which opts the whole app into per-request dynamic rendering (an accepted tradeoff: a per-request nonce is fundamentally incompatible with static prerendering) and lets Next auto-nonce its own scripts. Verified by diffing the CSP header's nonce against every `<script>` tag's `nonce` attribute in the served production HTML (exact match, zero un-nonced tags) and by a headless-browser run confirming `POST /api/auth/login` actually fires with zero CSP console errors. **The lesson that generalizes**: a nonce-based nginx/Next.js-style CSP has two independent halves — header generation and render-side propagation — and green tests plus a successful build verify neither. Only a live production browser console (or the exact diff above) catches a half-wired one.

**Found during the UI redesign pass**: `img-src` was `'self' data: blob:` only, which never accounted for the Vercel Blob storage host (`https://*.public.blob.vercel-storage.com`) added when trainer signature and certificate template background uploads moved off local disk (see "File uploads" above and `imageUrl.ts`'s `TRUSTED_BLOB_HOST_PATTERN`). In production, every uploaded signature thumbnail and template background image would have been silently blocked by CSP — the same class of "looks fine until you check a real browser" bug as the two above, just on `img-src` instead of `script-src`. Fixed by adding the Blob host explicitly to `img-src` in `src/middleware.ts`; caught this time by design review rather than by a live failure, since the redesign was the first UI work to render those images prominently (a signature `<img>` and a template's `background-image`).

## Rate limiting & abuse resistance

- Public verification (`publicVerifyRateLimiter`) and login (`loginRateLimiter`) are both rate-limited per client IP (`src/lib/rateLimit.ts`), covering the spec's "rate-limit the public verify endpoint against scraping/enumeration" requirement.
- Verification scans are logged (`verification_logs`) with a SHA-256 hash of the client IP rather than the raw address, and a truncated user-agent — enough for abuse analytics without storing raw visitor IPs.
- **Known limitation, sharper on serverless than originally scoped**: the limiter is an in-process `Map`. On a traditional single long-running server this only matters if you scale to multiple replicas; on Vercel, *every request can already land on a different serverless instance*, so in practice the limit resets far more often than the "per 60s/5min window" the code implies. It still helps against a single warm instance being hammered, and none of the app's actual trust guarantees (hash check, auth, CSRF) depend on it — but don't rely on it as your only anti-scraping/anti-brute-force control in production. See `DEPLOY.md` for the recommended fix (a shared store like Vercel KV/Upstash Redis, or Vercel's edge Firewall rate-limiting rules).

## Authorization boundaries

- Trainers cannot be newly assigned to a program once marked `inactive` (enforced server-side in `POST /api/programs/:id/trainers`), while certificates already issued under a since-deactivated trainer remain valid, per the spec.
- Participants with any issued certificate cannot be deleted (`DELETE /api/participants/:id` returns `409`) — certificate/participant history is never silently broken.
- Every mutation (create/update/revoke/reissue/bulk-import/login/logout) is written to `audit_logs` with the acting admin's id.

## What was verified, not just written

All of the above was exercised against a real (temporary) Postgres database via Vitest integration tests that call the actual Next.js route handlers — not mocked — including: unauthenticated requests being rejected, duplicate-email conflicts, tamper detection (hash mismatch → `invalid`), revoke/reissue state transitions, rate-limit enforcement after 30+ requests, and the frozen-snapshot immutability property. The full suite (96 tests) is run with `npm test`. The build was also run end-to-end manually against a live dev server on Postgres: login, trainer/program/participant creation, certificate generation, on-demand QR/PDF output, and public verification all confirmed working, alongside the security headers, auth redirect, and CSRF rejection.

## Known dependency vulnerabilities (`npm audit`)

- **`next@14.2.x`**: several published advisories (DoS via Server Components/Server Actions, request smuggling in rewrites, SSRF in rewrites/Server Actions, cache poisoning) apply to the 14.x line generally; the only fix path per `npm audit` is a major upgrade to Next 16, which is a breaking change not attempted in this pass to avoid shipping an unvalidated framework migration alongside the feature work. Track and schedule this upgrade separately, then re-run the full test suite and a manual smoke test.
- **`xlsx` (SheetJS)**: no fix currently available upstream for a prototype-pollution and ReDoS advisory. Exposure here is limited to admin-uploaded `.xlsx` bulk-participant files (`POST /api/programs/:id/participants/bulk`) — not reachable by unauthenticated users — but a malicious `.xlsx` from a lower-privileged Admin/Program Coordinator account could still trigger it. If this is a concern for your deployment, restrict bulk import to `.csv` only, or swap in a maintained alternative when one exists.

## Out of scope for this pass

- No admin account lockout beyond IP-based rate limiting (no per-account lockout/backoff).
- No 2FA for admin accounts.
- No dependency vulnerability scanning wired into CI (run `npm audit` periodically).
- No secrets manager integration — secrets are read from environment variables (`.env`, excluded from git via `.gitignore`); deploy with your platform's secret store rather than committing a populated `.env`.
